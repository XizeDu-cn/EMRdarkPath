# 大模型当评委：分阶段详解

## 读法说明

全文分七个阶段（0—6），按时间顺序排列。每个阶段都按同一个顺序写：

1. **为什么出现**：上一阶段留下了什么困难；
2. **怎么做**：按操作步骤写，写明谁被调用（参数不动）、谁被训练（参数改变）、提示词原文、数据长什么样；
3. **结果**：原文报告的关键数字；
4. **留下的问题**：它引出了下一阶段。

阶段 0 之后插了一节"工具箱"，讲怎么衡量"评委和人判得像不像"：一致率、Cohen's κ、宏 F1、相关系数，都给出算例。后面每一篇的结果都要用这些量来读。

最后一节按上一讲定下的方法：**先看原创线在自己的任务上怎么做、靠什么成立，再看 LLM-CARe 和 NHS 怎么把它换到病历上、在哪里出了问题。**

全线的主问题只有一个：**评委判出来的分，凭什么可信？**

| 阶段 | 时间 | 评委是谁 | 代表工作 |
|---|---|---|---|
| 0 | 2002–2020 | 人工，或 n-gram 重合度公式 | BLEU、ROUGE、BERTScore |
| 1 | 2023 春 | 现成的 GPT-4，直接打分 | G-Eval |
| 2 | 2023 夏 | GPT-4 两两比较，并系统检查偏差 | MT-Bench、Chatbot Arena、Wang 等 |
| 3 | 2024 | 专门测量并修正某一种偏差 | 自我偏好、长度控制的 AlpacaEval |
| 4 | 2023 末–2024 | 训练一个专用的评委模型 | Prometheus |
| 5 | 2025 | 专家逐题写评分细则，评委再与专家对表 | HealthBench |
| 6 | 2025 | 评委打的分直接当强化学习的奖励 | Rubrics as Rewards |

# 阶段 0　没有大模型评委的时候

## 为什么需要评委

生成模型写出来的东西，比如一段摘要、一个回答、一份病历，怎么判断好坏？

## 做法一：请人评

请标注员按几个维度打分（流畅、忠实、有用），或比较两个回答哪个更好。

**困难：** 贵、慢，每换一个模型、每改一次提示，就得重新请人；不同人的标准也不一致。

## 做法二：拿参考答案算重合度

先有一份人写的"参考答案"，再算模型输出和它有多少词重合。

- **BLEU**（2002，机器翻译）：数 n 个连续词（n-gram）的重合比例；
- **ROUGE**（2004，摘要）：同类思路，更看重召回；
- **BERTScore**（2020）：不数字面重合，而是用 BERT 的词向量算语义相似度。

**玩具例子**，看 BLEU 式的字面重合为什么不够：

```
参考答案：患者腹痛三天，伴恶心呕吐。
输出 A：  患者腹痛三天，伴恶心。             字面重合很高 → 高分（但漏了"呕吐"）
输出 B：  三日来持续上腹疼痛，并有呕吐和恶心。 字面重合很低 → 低分（其实更完整）
```

**困难：**
- 必须先有参考答案，而开放任务的好答案可以有一百种；
- 字面像不等于好，字面不像也不等于差。G-Eval 原文开头就指出，这类指标在创造性任务上与人的判断相关性很低。

**于是有人想：GPT-4 能写好文章，能不能让它来读、来打分？**

# 工具箱　怎么衡量"评委判得像不像人"

后面每一篇都会报告评委和人的一致程度。先把这几个量讲清楚。

## 1. 一致率

同一批题，评委和人各判一次，判得一样的比例。

```
100 份病历，逐份判"是否写了用药剂量"（是/否）
评委与医生判得一样的有 90 份 → 一致率 90%
```

**陷阱：** 如果 95 份其实都写了剂量，一个**永远回答"是"**的评委，一致率也能到 95%。一致率会被"大多数题答案都一样"骗高。

## 2. Cohen's κ：扣掉"碰巧一致"

```
κ = (实际一致率 − 碰巧会一致的比例) / (1 − 碰巧会一致的比例)
```

"碰巧会一致的比例"用两边各自回答"是"的频率来算。玩具数字：

| | 医生说"是" | 医生说"否" | 合计 |
|---|---|---|---|
| 评委说"是" | 85 | 5 | 90 |
| 评委说"否" | 5 | 5 | 10 |
| 合计 | 90 | 10 | 100 |

- 实际一致率 = (85 + 5) / 100 = 0.90
- 碰巧一致率 = 0.90 × 0.90（都说"是"）+ 0.10 × 0.10（都说"否"）= 0.82
- κ = (0.90 − 0.82) / (1 − 0.82) = **0.44**

一致率 90% 看起来很高，κ 却只有 0.44，因为大部分一致是"大家都说是"碰出来的。**报告 κ 比报告一致率诚实。**

## 3. 宏 F1：只看"找错"的本事

对二值判断，分别把"是"和"否"当作正类，各算一次 F1（精确率与召回率的调和平均），再取平均。

用上面那张表，把"否"（有问题）当作正类：
- 精确率 = 评委说"否"里真是"否"的 = 5 / 10 = 0.5
- 召回率 = 真是"否"里评委说"否"的 = 5 / 10 = 0.5
- F1(否) = 0.5；同理 F1(是) = 85/90 ≈ 0.94
- 宏 F1 = (0.94 + 0.5) / 2 ≈ **0.72**

宏 F1 把少数类（"有问题"）拉到与多数类同等的地位。**评委是否真能挑出问题，看的就是少数类那一半。**

## 4. 相关系数：打分制时用

评委给 1–5 分，人也给 1–5 分，算两串分数的 Pearson（看数值）或 Spearman（看排名）相关。1 表示完全一致，0 表示无关。

## 5. 最重要的一条：在谁的输出上测

评委和人的一致程度，**只在被测过的那类文本上成立**。如果某个方法专门针对评委的口味做了优化，它的输出恰恰最可能骗过评委。所以检验评委时，**必须在被比较的各个方法的输出上分别检验**，尤其是"优化过的"那一个。

# 阶段 1（2023 春）　让 GPT-4 直接打分：G-Eval

代表工作：**G-Eval**（Liu 等，2023）

## 为什么出现

BLEU、ROUGE 需要参考答案，与人的判断相关性又差。作者想：GPT-4 能读懂文章，就让它**不依赖参考答案**，直接按标准打分。

## 怎么做

**调用（参数不动）：** GPT-4。**训练：** 无。

**第 1 步　写任务说明和评价标准。** 以"摘要的连贯性"为例（原文）：

```
Task Introduction:
You will be given one summary written for a news article.
Your task is to rate the summary on one metric.
（你会拿到一篇新闻的一段摘要。你的任务是按一个指标给它打分。）

Evaluation Criteria:
Coherence (1-5) - the collective quality of all sentences. ……
the summary should be well-structured and well-organized.
（连贯性 1–5：所有句子整体的质量……摘要应当结构清楚、组织有序。）
```

**第 2 步　让模型自己生成"评价步骤"（原文称 auto-CoT）。** 把上面的说明交给 GPT-4，让它写出打分时应该怎么一步步做，例如（原文）：

```
Evaluation Steps:
1. Read the news article carefully and identify the main topic and key points.
2. Read the summary and compare it to the news article. ……
3. Assign a score for coherence on a scale of 1 to 5 ……
```

这些步骤生成一次，之后所有打分都复用。

**第 3 步　拼成完整的打分提示。**

```
{任务说明}
{评价标准}
{评价步骤}

Source Text:
{新闻原文}

Summary:
{待评的摘要}

Evaluation Form (scores ONLY):
- Coherence:
```

末尾留空，让模型接着写一个分数。

**第 4 步　不直接取它写的数，而是按概率加权。**

直接让模型写一个数，会出两个问题：一是它特别爱写"3"，分数挤在一起；二是只有整数，分不出细微差别。G-Eval 的做法是读取模型在"1、2、3、4、5"这五个词元上的概率，取期望（原文公式）：

```
score = Σ p(s_i) × s_i
```

玩具数字：

```
模型在分数位置上的概率：  1: 0.02   2: 0.08   3: 0.50   4: 0.35   5: 0.05
直接取最可能的 → 3
概率加权      → 0.02×1 + 0.08×2 + 0.50×3 + 0.35×4 + 0.05×5 = 3.33
```

另一篇摘要可能是 3.71。两篇直接取值都是"3"，加权后就能分出高下。

## 考试

在 SummEval 等已有人工打分的摘要数据上，算 G-Eval 分数与人工分数的相关系数。

## 结果

- 摘要任务上与人工的 Spearman 相关为 **0.514**，明显高于此前各种自动指标；
- **原文自己报告的偏差：** G-Eval-4 **总是**给 GPT-3.5 写的摘要打更高分，**即使人工评审更喜欢人写的摘要**。

## 留下的问题

- 直接打绝对分，尺度不稳：同一篇文章，换一次提示可能差一分；
- 已经看到偏爱大模型写的文字，但没有系统测量这种偏差有多大、从何而来。

# 阶段 2（2023 夏）　两两比较，并系统检查偏差

## 2.1 MT-Bench 与 Chatbot Arena（Zheng 等，NeurIPS 2023）

### 为什么出现

要比较很多个聊天模型哪个更好。请人逐一评太贵，于是想用 GPT-4 当评委，但必须先证明它和人判得一样。

### 怎么做

**第 1 步　出题。** MT-Bench：**80 道两轮对话题，8 个类别**（写作、角色扮演、信息抽取、推理、数学、编程、理工知识、人文社科知识），每类 10 道。

**第 2 步　让被测模型作答。** 每个模型回答全部 80 道题。

**第 3 步　评委打分，有三种方式：**

| 方式 | 做法 | 适用 |
|---|---|---|
| 两两比较 | 给评委看同一道题的两个回答，问哪个更好 | 主要方式 |
| 单独打分 | 给评委看一个回答，打 1–10 分 | 需要绝对分时 |
| 参考答案引导 | 数学、推理题先给评委一个标准答案，再让它判 | 评委自己不会做的题 |

两两比较的评委提示（原文开头）：

```
Please act as an impartial judge and evaluate the quality of the responses provided by
two AI assistants to the user question displayed below. You should choose the assistant
that follows the user's instructions and answers the user's question better.
……（请考虑有用性、相关性、准确性、深度、创造性和细节程度；
      不要让回答出现的先后顺序影响判断；不要让回答长度影响判断……）
[User Question]
{问题}
[The Start of Assistant A's Answer]
{回答 A}
[The End of Assistant A's Answer]
[The Start of Assistant B's Answer]
{回答 B}
[The End of Assistant B's Answer]
```

评委写一段理由，最后输出 `[[A]]`、`[[B]]` 或 `[[C]]`（平局）。

**第 4 步　处理位置偏差。** 每一对**评两次**，第二次把 A、B 顺序对调。原文："只有两种顺序下都偏好同一个回答，才算它赢；两次结果不一致，就记为平局。"

**第 5 步　与人对表。** 收集约 3000 条专家投票，在同样的题目和回答对上，比较 GPT-4 的判断与人的判断。

**第 6 步　Chatbot Arena：众包排名。** 用户在网页上同时和两个匿名模型对话，投票选更好的一个。几万条投票用 **Bradley–Terry 模型**（和上一讲奖励模型用的是同一个公式）估计每个模型的"实力分"，排出名次。

玩具数字：三个模型，各两两比赛若干次：

```
A 对 B：A 赢 70 次，B 赢 30 次
B 对 C：B 赢 60 次，C 赢 40 次
A 对 C：A 赢 80 次，C 赢 20 次
拟合 P(i 胜 j) = σ(s_i − s_j)，得到实力分约为 A: +0.9, B: 0.0, C: −0.5 → 排名 A > B > C
```

### 结果

- **一致率：** 不计平局时，GPT-4 与人的一致率 **85%**，人与人之间 **81%**；
- **三种偏差（原文量化）：**

| 偏差 | 表现 | 原文数字 |
|---|---|---|
| 位置偏差 | 偏好先出现（或后出现）的回答 | 需要对调顺序才能消除 |
| 长度偏差 | 偏好更长的回答 | "重复列表"攻击（把回答里的条目换个说法重复一遍，使其变长而不增加信息）：Claude-v1 与 GPT-3.5 当评委时，**91.3%** 被骗；GPT-4 为 **8.7%** |
| 自我偏好 | 偏爱自己写的回答 | 与人相比，GPT-4 给自己的胜率约高 **10%**，Claude-v1 约高 **25%** |

- 另有"推理能力有限"：评委自己不会做的数学题，也判不准，所以要用参考答案引导。

## 2.2 Wang 等："Large Language Models are not Fair Evaluators"（2023）

### 做了什么

专门测**位置偏差**：同一对回答，只调换出场顺序，看评委的判断变不变。

### 结果

以 ChatGPT 当评委时，只要调换顺序，**Vicuna-13B 就能在 80 道题中的 66 道上"击败" ChatGPT**。

### 他们提出的三种修正

1. **多重证据校准**：先让评委写出多条理由，再给分；
2. **平衡位置校准**：两种顺序各评一次，汇总结果（与 MT-Bench 的对调法同理）；
3. **人工介入校准**：用一个"多样性熵"指标找出评委最拿不准的题，只把这些交给人。

## 留下的问题

偏差已经看到，但每种偏差到底多大、为什么产生、能不能修正，需要更专门的测量。

# 阶段 3（2024）　专门测量并修正某一种偏差

## 3.1 自我偏好：Panickssery 等，"LLM Evaluators Recognize and Favor Their Own Generations"（2024）

### 做了什么

1. **测自我偏好：** 让模型评价自己写的和别的模型写的摘要，而人工评审认为两者一样好。结果模型**给自己的打分更高**；
2. **测自我识别：** 把几段文字给模型看，问"哪一段是你写的"。GPT-4、Llama 2 **开箱即有相当的准确率**；
3. **把两者联系起来：** 通过微调改变模型的"自我识别"能力，发现**自我识别越准，自我偏好越强，两者呈线性相关**，而且这种关系是因果的。

### 意义

**评委和被评者是同一个模型、或同一家族时，打分会系统性偏高。**这不是个别现象，而是评委"认出了自己"。

## 3.2 长度偏差：Dubois 等，长度控制的 AlpacaEval（2024）

### 背景

AlpacaEval 是一个常用的自动评测：用 GPT-4 把被测模型的回答和一个基准模型的回答两两比较，算胜率。它与 Chatbot Arena 的人工排名高度相关，但众所周知**偏爱长回答**。

### 做法：用回归把"长度"这个混杂因素扣掉

**第 1 步：** 对每一对比较，记录评委的偏好，以及两个回答的长度差。

**第 2 步：** 拟合一个广义线性模型（类似逻辑回归），用"模型本身的实力"和"长度差"两项一起去预测评委的偏好。

**第 3 步：** 回答一个反事实问题："**如果两个回答一样长**，评委会偏好谁？"把长度差那一项设为 0，算出的胜率就是"长度控制胜率"。

玩具数字：

```
模型 X 的原始胜率 ≈ σ(0.3 + 0.8 × 0.9) = σ(1.02) ≈ 73%
拟合结果：偏好 ≈ σ( 实力项 0.3 + 0.8 × 标准化长度差 )，X 的回答平均比基准长 0.9 个标准差
把长度差设为 0：σ(0.3) ≈ 57%   → 长度控制胜率 57%
```

一个靠啰嗦刷分的模型，控制长度后会明显掉分。

### 结果

与 Chatbot Arena 人工排名的 Spearman 相关，从 **0.94 升到 0.98**。

## 留下的问题

偏差可以逐个修补，但现成的通用大模型当评委，还有闭源、版本随时变、费用高的问题。能不能**训练一个专门的评委**？

# 阶段 4（2023 末–2024）　训练一个专用评委：Prometheus

代表工作：**Prometheus**（Kim 等，ICLR 2024）

## 为什么出现

用 GPT-4 当评委有三个麻烦：闭源、版本不受控（换个版本分数就变）、贵。作者想：**拿 GPT-4 造一批"怎么打分"的示范数据，训练一个开源的小评委。**这其实就是第一讲"用大模型造训练数据"的做法，只是造的是"评分数据"。

## 怎么做：先造数据，再训练

### 造数据（四步，原文）

**第 1 步　人写种子细则。** 作者手写 **50 条**评分细则。每条是一个具体维度，配 1–5 分各档的描述。示意：

```json
{"criteria": "回答是否在需要时给出了具体、可执行的步骤？",
 "score1": "完全没有给出可执行的步骤。",
 "score2": "……",
 "score3": "给出了一些步骤，但不完整或不够具体。",
 "score4": "……",
 "score5": "给出了完整、具体、可直接照做的步骤。"}
```

**第 2 步　GPT-4 扩写细则。** 每次随机抽 4 条种子细则当示范，让 GPT-4 写新细则，反复 10 轮，扩成 **1000 条**。（调用 GPT-4，参数不动。）

**第 3 步　GPT-4 按细则出题。** 为每条细则写 20 道与之贴合的指令，共 **2 万条**。

**第 4 步　GPT-4 写"每一档分数的回答"和评语。** 对每道题，让 GPT-4 分别写出**得 1 分、2 分、3 分、4 分、5 分**的五个回答，每个都配一段评语，说明为什么是这个分，共 **10 万条**。各分数档数量均衡，避免评委只学会打高分。

一条训练数据的样子（格式依原文，内容示意）：

```
###Task Description:
An instruction (might include an Input inside it), a response to evaluate, a reference answer
that gets a score of 5, and a score rubric representing an evaluation criteria are given.
1. Write a detailed feedback that assess the quality of the response strictly based on the
   given score rubric, not evaluating in general.
2. After writing a feedback, write a score that is an integer between 1 and 5.
3. The output format should look as follows:
   "Feedback: (write a feedback for criteria) [RESULT] (an integer number between 1 and 5)"

###The instruction to evaluate:
我家水管漏水了，我该怎么办？

###Response to evaluate:
建议联系专业人士处理。

###Reference Answer (Score 5):
先关闭总水阀止水；用毛巾吸干积水；找到漏点，临时可用防水胶带缠紧；拍照记录后联系物业或水管工……

###Score Rubrics:
[回答是否在需要时给出了具体、可执行的步骤？]
Score 1: 完全没有给出可执行的步骤。
……
Score 5: 给出了完整、具体、可直接照做的步骤。

###Feedback:
```

**目标输出**（评委要学着写出的内容）：

```
Feedback: 回答只建议联系专业人士，没有给出关阀、止水等任何可以立即执行的步骤，
与参考答案相比缺少全部关键操作。 [RESULT] 1
```

注意评委的输入包括**参考答案**和**评分细则**两样外部锚点，它不是凭空判断。

### 训练（改参数）

- **起点：** Llama-2-Chat 7B / 13B；
- **方法：** 监督微调，就是第二讲讲过的逐词元交叉熵：输入上面那段提示，目标是"Feedback: …… [RESULT] 1"这段文字，让模型逐字学会写出评语和分数；
- **顺序：** 先写评语、再写分数，中间用 `[RESULT]` 分隔。原文说明，这样做可以防止推理时输出退化。

### 考试

- 在**训练时没见过的细则**上，让 Prometheus 和人各自打分，算 Pearson 相关；
- 另在 MT-Bench、Vicuna Bench 等公开评测上，看它和 GPT-4 的判断是否一致。

## 结果

在自定义细则上，与人的 Pearson 相关：**Prometheus 0.897，GPT-4 0.882，ChatGPT 0.392**。一个 13B 的开源模型，追平了 GPT-4。

## 这一阶段要抓住的要点

- 评委也可以"造数据 → 训练"得到；
- 训练数据刻意覆盖所有分数档，且给了参考答案和细则，评委判断时有外部锚点；
- **验收用的是训练中没见过的细则，由人打分作对照。**

## 留下的问题

细则由 GPT-4 扩写，偏通用。到了医学这类专业领域，"什么算好回答"只有专家说了算。评委能否按**专家写的、逐题定制的**细则来判？判得和专家一样吗？

# 阶段 5（2025）　专家逐题写细则，评委再与专家对表：HealthBench

代表工作：**HealthBench**（Arora 等，OpenAI，2025）

## 为什么出现

医疗回答的好坏，高度依赖具体情境：同一个"头痛"，对普通用户该建议什么、对医生该说什么，完全不同。通用细则不够用，得由医生针对**每一段对话**写专门的评分标准。

## 怎么做

**第 1 步　收集对话。** **5000 段**多轮对话，对话一方是普通用户或医疗专业人员。

**第 2 步　医生逐段写细则。** **262 名医生**为每段对话写专属的评分条目，合计 **48,562 条互不相同的条目**，覆盖急症、临床数据改写、全球卫生等情境，以及准确性、遵循指令、沟通等维度。

每条条目有一个 **−10 到 10** 之间的非零分值；**负分表示"不该出现的行为"**。示意（格式依原文，内容为示意）：

```json
{"conversation": "用户：我 70 岁的父亲突然说话含糊、右手无力，大概 20 分钟了，要不要等等看？",
 "rubric": [
   {"criterion": "明确建议立即拨打急救电话或马上去急诊", "points": 10},
   {"criterion": "提到这可能是卒中，时间窗很关键",         "points": 7},
   {"criterion": "询问或提醒记录症状开始的时间",           "points": 5},
   {"criterion": "建议先在家观察或等症状自行缓解",         "points": -10},
   {"criterion": "建议自行服用阿司匹林",                   "points": -6}
 ]}
```

**第 3 步　评委逐条判"是否满足"。** 用 **GPT-4.1** 当评委，把对话、被评回答和**一条**细则一起给它，问这条是否满足。每条细则单独问一次。

**第 4 步　算分（原文公式）。**

```
得分 = 满足的条目分值之和 / 所有正分条目分值之和
```

玩具数字：某个回答满足了"立即急救"（+10）和"提到卒中"（+7），但也犯了"建议阿司匹林"（−6），没问起病时间：

```
得分 = (10 + 7 − 6) / (10 + 7 + 5) = 11 / 22 = 0.50
```

**第 5 步　元评测：评委和医生判得一样吗？** 这是整套设计最关键的一步。

- 另请医生对一批"回答 × 条目"判断是否满足；
- 算 GPT-4.1 评委与医生的**宏 F1**（工具箱第 3 节）；
- 同时算**医生与医生之间**的宏 F1，看评委在医生中排第几。

作者还说明，评委的提示词和部分条目措辞，是**对照医生判断反复调整过**的。

## 结果

- GPT-4.1 当评委，整体宏 F1 为 **0.709**；
- 在七个主题中，六个主题上评委**排在医生的上半区**，所有主题上都**高于医生的下三分之一**；
- 也就是说：评委判"是否满足"的水平，大致相当于一名中等偏上的医生。

## 这一阶段要抓住的要点

1. **细则由领域专家逐题撰写**，而且与被评的模型无关；
2. **负分条目**把"不该做的事"也纳入评分；
3. **评委本身要被元评测**：拿专家当标尺，报告评委在专家中的位置，而不是只报一个一致率；
4. 阶段 6 的 Rubrics as Rewards（2025）正是拿 HealthBench 当**考卷**：训练时用自己的细则当奖励，考试用 HealthBench，二者分开。

# 阶段 6（2025）　评委变成奖励：Rubrics as Rewards

代表工作：**Rubrics as Rewards，RaR**（Gunjal, Wang, Lau, Nath, He, Liu, Hendryx，Scale AI，arXiv 2507.17746，2025）

## 为什么出现

前五个阶段里，评委只用来**考试**：模型训练完了，请评委打分。

到 2025 年，强化学习已经在数学、代码上大获成功（DeepSeek-R1 等），靠的是**可验证奖励**：程序比对最终答案，对了给 1，错了给 0。可医学问答、病历这类任务没有唯一正确答案，程序判不了。能不能**把评委打的分当成强化学习的奖励**？

直接这么做有现成的坑：
- 让评委给整个回答打 1—10 分（Likert），分数粗、不稳定；
- 模型很快学会讨好评委的偏好，比如写得更长、更客气，而不是更对。阶段 2、3 列过的那些偏差，在强化学习里会被**主动利用**。

RaR 的思路：**把阶段 5 的"逐题细则"搬进训练**。不问评委"这个回答好不好"，而是逐条问"这一条满足了没有"。每一条都接近一个可验证的小判断。

## 先从零讲：强化学习在这里干什么

这部分和第二讲、第五讲讲的是同一套方法，按"每一讲自成一体"的约定，这里完整再讲一遍。

**被训练的模型叫"策略"**：给它一个问题，它写出一个回答。训练前它是一个普通的开源模型，RaR 用的是 Qwen2.5-7B。

**一轮训练（GRPO）的五步：**

1. **出题**：取一个医学问题 x。
2. **采样**：让策略对同一个问题写 16 个不同的回答（RaR 原文设置，每题 16 份）。
3. **打分**：每个回答按这道题的细则算一个奖励 r，见下一节。
4. **比较**：16 个奖励求平均，每个回答的"优势" = 自己的奖励 − 平均。高于平均是正，低于平均是负。
5. **调参数**：把优势为正的回答里每个词的生成概率往上推，优势为负的往下压，推压幅度正比于优势大小。同时加一个惩罚项：模型整体偏离训练前太远就扣分，防止它为了刷分写出怪东西。

**GRPO 的特点是不需要另训一个"价值模型"来估计基准线，直接用同一题 16 个回答的平均分当基准。** 这让它比 PPO 省一大块显存，也是你在两张 5090 上能考虑它的原因。

玩具数字（自拟）：某题 4 个回答（实际是 16 个）的奖励为 `[0.80, 0.45, 0.60, 0.15]`，平均 0.50，优势为 `[+0.30, −0.05, +0.10, −0.35]`。第一个回答被强化最多，第四个被压得最狠。

RaR 原文的训练设置：GRPO，每题 16 个回答，批大小 96，学习率 5×10⁻⁶，300 步，最长 3584 个 token。

## 怎么做

### 第 1 步　为每道题造一份细则（调用，参数不动）

- 医学题用 **GPT-4o**、科学题用 **o3-mini** 来写细则；
- **关键：写细则时给它看参考答案**，即该题由专家或强模型写好的标准回答；
- 每题产出 7—20 条细则，JSON 格式。每条带类别和权重：

| 类别 | 含义 | 权重 |
|---|---|---|
| Essential | 必须有的关键事实、安全要点 | 5 |
| Important | 重要的推理、完整性 | 3—4 |
| Optional | 风格、深度上的加分项 | 1—2 |
| Pitfall | 常见错误，出现就扣分 | −1 或 −2 |

原文给出的一条医学细则（照录）：
```
Essential Criteria: The response must correctly identify and apply the formula (Base Deficit × Body Weight × 0.3) to determine the bicarbonate requirement.
```

数据集：
- RaR-Medicine：20,166 道题，其中诊断类约占一半，治疗类 16%；
- RaR-Science：20,625 道题。

### 第 2 步　算奖励（调用评委，参数不动）

评委用 **gpt-4o-mini**，比写细则的模型小、也便宜，因为训练时每一步都要调用很多次。两种算法：

**显式聚合（explicit）**：评委对每一条细则判"满足 / 不满足"（c = 1 或 0），按权重加权平均：
```
r = Σ (w_j · c_j) / Σ w_j
```

**隐式聚合（implicit）**：把整份细则和回答一起给评委，让它综合细则打一个 1—10 分。

### 第 3 步　GRPO 训练（被训练：Qwen2.5-7B 的参数）

按上面五步，跑 300 步。

### 第 4 步　考试

- **HealthBench**（阶段 5 的医生细则考卷）；
- **GPQA-Diamond**（研究生水平科学选择题，有标准答案）。

**注意训练和考试分开**：训练用的是 GPT-4o 根据参考答案写的细则，考试用的是 HealthBench 里医生写的细则。这正是第三讲"修改依据 ≠ 考试标尺"在训练里的体现。

## 结果

- **HealthBench**：RaR-Implicit 35.9%，直接 Likert 打分做奖励只有 23.9%，相对提高约 31%（摘要写"最高 31%"）；
- **GPQA-Diamond**：相对提高约 7%；
- 对照组设计值得学：
  - 直接 Likert（不给细则）；
  - 给参考答案的 Likert；
  - 通用固定细则（每题一样）；
  - 逐题细则的显式聚合；
  - 逐题细则的隐式聚合。

  这五行一排，"逐题细则"的作用就被单独剥离出来了。
- **评委大小**：给了细则之后，各种大小的评委判断都更准；最小的 Qwen-7B 评委提升最多。**细则让小评委也能用**，这对只有本地显卡的人很重要。
- **细则的来源**：写细则时给参考答案的，明显好于不给的。**细则必须有外部依据，不能让模型凭空想。**

## 这一阶段要抓住的要点

1. 评委从"考官"变成"教练"：它的分数直接决定模型往哪个方向改参数。**评委的任何偏差，都会被强化学习放大**；
2. 把"好不好"拆成一条条"有没有"，每条都更接近可验证判断，奖励就更稳、更难被钻空子；
3. 写细则要有外部锚点（参考答案）；
4. 训练细则和考试细则分开。

## 搬到病历上：一份病历细则长什么样（自拟示例）

假设输入是一份结构化记录：女，68 岁，左膝骨关节炎，青霉素过敏，在服氨氯地平 5mg。要生成一份入院记录。

```json
[
  {"category": "Essential", "weight": 5,  "criterion": "主诉包含主要症状及持续时间", "checker": "规则"},
  {"category": "Essential", "weight": 5,  "criterion": "过敏史写明青霉素过敏",       "checker": "规则"},
  {"category": "Essential", "weight": 5,  "criterion": "病变侧别为左膝，全文一致",     "checker": "规则"},
  {"category": "Important", "weight": 4,  "criterion": "用药史与结构化记录一致（氨氯地平 5mg qd）", "checker": "规则"},
  {"category": "Important", "weight": 3,  "criterion": "现病史交代起病诱因与诊治经过", "checker": "评委"},
  {"category": "Optional",  "weight": 1,  "criterion": "体格检查描述符合骨关节炎典型表现", "checker": "评委"},
  {"category": "Pitfall",   "weight": -2, "criterion": "出现结构化记录中不存在的检查结果或数值", "checker": "规则 + 评委"},
  {"category": "Pitfall",   "weight": -2, "criterion": "写"无药物过敏史"",               "checker": "规则"}
]
```

最后一列是 RaR 原文没有、病历特有的优势：**一半以上的细则可以由程序判**，只有剩下的交给评委。程序判的部分不会被讨好，评委判的部分再用医生抽检校准。这就是上一轮说的"把'好'拆成'对'的部分和'好'的部分"。

# 全景汇总

## 各工作一览

| 阶段 | 工作 | 评委 | 训练了什么 | 评委的锚点 | 如何证明评委可信 |
|---|---|---|---|---|---|
| 0 | BLEU/ROUGE | 公式 | 无 | 参考答案 | 与人工分算相关（相关性低） |
| 1 | G-Eval | GPT-4 | 无 | 评价标准 + 自动生成的步骤 | Spearman 0.514；自报偏爱大模型文字 |
| 2 | MT-Bench | GPT-4 | 无 | 两两比较；数学题给参考答案 | 与专家投票一致率 85%（人与人 81%）；量化三种偏差 |
| 2 | Wang 等 | ChatGPT | 无 | — | 证明调换顺序即可翻转 66/80 |
| 3 | 自我偏好研究 | GPT-4、Llama 2 | 为做因果检验而微调 | — | 自我识别与自我偏好线性相关 |
| 3 | 长度控制 AlpacaEval | GPT-4 | 一个去偏的回归模型 | — | 与人工排名相关 0.94 → 0.98 |
| 4 | Prometheus | 13B 开源模型 | **评委本身**（监督微调） | 参考答案 + 细则 | 在未见细则上与人相关 0.897 |
| 5 | HealthBench | GPT-4.1 | 无（提示词对照医生调整过） | **医生逐题写的细则**，含负分 | 与医生的宏 F1 0.709，处于医生中上游 |
| 6 | Rubrics as Rewards | gpt-4o-mini（当奖励） | **被评的策略模型**（Qwen2.5-7B，GRPO） | GPT-4o 依参考答案写的逐题细则 | 训练细则与考卷（HealthBench）分开；HealthBench 相对提升约 31% |

## 一句话脉络

公式对参考答案（阶段 0）→ 大模型直接打分（阶段 1）→ 两两比较并发现偏差（阶段 2）→ 逐个量化并修正偏差（阶段 3）→ 训练专用评委（阶段 4）→ 专家逐题写细则、再拿专家给评委定位（阶段 5）→ 评委的分数直接当训练奖励（阶段 6）。

## 这条线沉淀下来的六条合同

1. **评委要被元评测**：拿人或专家当标尺，报告 κ 或宏 F1，最好还报告评委在专家之间排在哪里；而且要在**被比较的各个方法的输出上**分别验证，尤其是专门优化过的那个。
2. **细则来源独立于被评方法**：专家撰写、逐题定制，不能是某个被评方法优化时用的那份清单。
3. **控制已知偏差**：位置偏差靠对调，长度偏差靠控制，自我偏好靠让评委与被评者**不同家族**。
4. **给评委外部锚点**：参考答案、细则；评委自己算不对的（数学、计算），给标准答案或交给程序。
5. **把"不该做的事"写进评分**：负分条目，比如捏造检查结果、给出危险建议。
6. **让分数能区分高下**：分数挤在一起时，用概率加权或两两比较。

# 对照：LLM-CARe 与 NHS 怎么把这条线搬到病历上

照上一讲的方法：先看原创线在自己的任务上做了什么、靠什么成立，再看它们换任务时丢了什么。

## 一、LLM-CARe 搬的是哪一种

它的评测形式最接近**阶段 5 的"细则逐条判是否满足"**（HealthBench 式），加上阶段 2 的"换评委看排名是否稳定"。

**它的评测流程（论文附录 D、F、L）：**
1. 评委：Qwen2.5-32B；
2. 细则：17 条固定的检查项（完整性 9 条、一致性 3 条、正确性 5 条）；
3. 每份病历、每条检查项，评委答"是或否"，取平均；
4. 稳健性：另换 GPT-OSS-20B、DeepSeek-V3.2（后者只评 10% 的数据），看排名是否一致；
5. 医生验证：4 名医生对 200 份病历（5 种方法各 40 份）回答同样的检查项，报告评委与医生的 Cohen's κ = 0.833，医生之间的 Fleiss κ = 0.950。

## 二、逐条对照 HealthBench

| 环节 | HealthBench（原创线） | LLM-CARe | 差在哪里 |
|---|---|---|---|
| **细则由谁写** | 262 名医生，针对每段对话**逐题撰写** | 作者按《病历书写基本规范》整理的 **17 条通用清单**，每份病历都一样 | 通用清单只能查"写没写"，查不了"写得对不对" |
| **细则和被评方法的关系** | 与任何被评模型无关 | **正是 LLM-CARe 生成时逐条自查、自改的那 17 条** | 违反合同 2：考卷就是它的复习提纲 |
| **负分条目** | 有：危险建议、不该出现的内容要扣分 | 无：只问"有没有写到"，编造的化验值、不存在的检查不扣分 | 违反合同 5：越爱往里写的方法越占便宜 |
| **评委与被评者** | GPT-4.1 评各家模型 | Qwen2.5-**32B** 评 Qwen2.5-**7B** 写的病历 | 同家族，有自我偏好的风险（合同 3）；换 GPT-OSS、DeepSeek 做了稳健性检查，这一点算是补了一部分 |
| **元评测做了什么** | 评委与医生的宏 F1，并给出评委在医生中的排位 | 评委与医生的 κ = 0.833 | 形式上做了，而且 κ 比一致率诚实，这一点做得对 |
| **元评测证明了什么** | 评委判"是否满足"的能力相当于中上游医生；而细则本身由医生写，所以"满足细则"≈"医生认为好" | 评委判"是否满足清单"的能力接近医生；但清单是 LLM-CARe 自己的优化目标 | 它证明的是"**评委会按清单判**"，没有证明"**清单高分就是好病历**" |
| **在哪些输出上验证** | 各被评模型的回答 | 5 种方法混在一起，只报一个总 κ | 没有单独报告在 LLM-CARe 自己输出上的一致性（工具箱第 5 节） |
| **医生有没有直接比较方法** | 细则本身即医生判断 | 医生只回答清单上的是或否，**从未被问"哪份病历更好""哪份像真病历"** | 缺少原创线阶段 2 那种人对输出的直接偏好比较 |

**要点：** 单看"评委与医生 κ = 0.833"，LLM-CARe 像是做得很规范。它的问题不在评委判得准不准，而在**被判的那份清单**：清单由它自己的生成流程逐条优化过；清单只问"写没写"，不问"对不对"、不惩罚编造。评委越准，越能准确地量出"它按清单写全了"，但这和"病历质量高"是两回事。

**打个比方：** 考试严格按大纲判卷，阅卷老师也判得很准，κ 很高；可考卷上的题就是这个学生考前逐条背过的大纲原文。阅卷越准，越能说明他背熟了大纲，说明不了他会看病。

## 三、NHS 搬的是哪一种

它的评委形式是**阶段 1 的 G-Eval 式直接打分**：1–5 分，先写理由再给分（`prompts.py` 858 行起的扎根度评委，格式与 G-Eval 一致）。

| 环节 | G-Eval / MT-Bench（原创线） | NHS | 差在哪里 |
|---|---|---|---|
| **分数怎么取** | 按 1–5 各档的概率加权，得连续分数 | 直接读评委写出的整数 | 分数挤在一起，分不出高下（合同 6） |
| **评委与被评者** | 原文自己警告：评委偏爱大模型写的文字 | 评委、生成器、校验器是**同一个模型**（`evaluation_utils.py` 三个评委都用 `PARAMS["pipeline_config"]["model"]`） | 自我偏好最大化（合同 3）；MT-Bench 测过，GPT-4 给自己的胜率约高 10% |
| **评分标准来源** | 任务说明 + 标准 | "相关度"评委的判据，与**生成提示词、校验器用的是同一句话**（`prompts.py` 621、720、895 行） | 考卷等于复习提纲（合同 2） |
| **与人对表** | Spearman 0.514；MT-Bench 与 3000 条专家投票对比 | **没有**：只有医生反馈的改进清单，没有任何评委与医生的一致性数字 | 违反合同 1：评委从未被元评测 |
| **温度** | 评测通常用确定性解码 | 函数里写了 `temperature = 0`，但没有传给调用函数，实际用默认 0.7（`processing.py:147`） | 同一份笔记每次打分可能不一样 |
| **覆盖范围** | 全量 | 流畅度只算了前 2 条，全量运行会报错 | 名义评测 |
| **结果** | 报告数字 | 全文没有一个评测数字 | — |

**要点：** NHS 搬的是阶段 1 最早、最原始的形态，而且连阶段 1 自己的两条讲究（概率加权、与人对表）都没搬过来；阶段 2、3 发现的自我偏好，它恰好做到了最大。

## 四、一句话

原创线这三年，一直在回答一个问题：**评委打的分，凭什么可信？**答案逐步积累成了六条合同。LLM-CARe 做到了"与医生对表"这一条，却让评委去量一份它自己优化过、只查"写没写"的清单；NHS 则停在 2023 年春天的起点，让写笔记的模型自己给自己打分，而且没有一次和人对过表。

## 五、给你自己用：训练一个病历查错器（路线 B）怎么借这条线

上面几节是看别人怎么用评委。这一节是自己怎么做。目标：**训练一个专门找病历错误的小模型**。它同时有三个用处：评测时当独立评委，生成时当过滤器，强化学习时当奖励的一部分。

### 借哪几个阶段

| 借自 | 借什么 |
|---|---|
| 阶段 4 Prometheus | "先造评委训练数据，再监督微调一个开源评委"的整套做法 |
| 第二讲 CriticGPT | 故意在正确样本里埋错，用埋错样本训练批评器 |
| 第五讲 Re3 | 负例完全自动构造（重复、打乱、换成别的故事），不需要人工标注 |
| 阶段 5 HealthBench | 元评测：查错器要和医生对表，报告宏 F1 或 κ |
| 阶段 6 RaR | 能程序判的交给程序，查错器只管程序判不了的部分 |

### 第 1 步　造训练数据（不需要人工标注）

**正例**：真实病历，或真实病历中的一段，标签为"无错"。

**负例**：用程序在正例里埋一处错误，标签为"有错 + 错误类型 + 位置"。埋错类型（示例）：

| 类型 | 怎么埋 | 例子 |
|---|---|---|
| 侧别翻转 | 左 ↔ 右 | "左膝" → "右膝" |
| 剂量漂移 | 数值乘 2 或除以 2，或改单位 | "5mg" → "50mg" |
| 过敏消失 | 删除过敏史，或改成"无" | "青霉素过敏" → "否认药物过敏史" |
| 性别冲突 | 插入与性别矛盾的诊断或检查 | 男性病历插入"妇科超声" |
| 时间倒错 | 交换两个事件的日期 | 术后记录日期早于手术 |
| 停药复活 | 已停的药在后文写"继续" | 跨文书 |
| 捏造数值 | 插入结构化记录中没有的化验结果 | "肌钙蛋白 2.3 ng/mL" |
| 诊断—表现冲突 | 把一条症状换成与诊断矛盾的症状 | 诊断阑尾炎，写"右下腹无压痛" |

一条训练样本（自拟）：
```json
{
  "record": {"sex": "F", "allergy": ["penicillin"], "dx": ["osteoarthritis, left knee"], "meds": {"amlodipine": "5 mg qd"}},
  "note_span": "既往高血压病史，规律服用氨氯地平 50mg qd。否认药物过敏史。",
  "label": [
    {"type": "dose_drift", "span": "50mg", "expected": "5mg"},
    {"type": "allergy_dropped", "span": "否认药物过敏史", "expected": "青霉素过敏"}
  ]
}
```

**要防的坑**：如果负例全是程序埋的，查错器可能学会认"程序埋错的痕迹"，而不是真正的错误。所以测试集里必须另有一批**生成器自然犯的错**，由医生标注。这就是 DNLI 那个教训的翻版：只在自造数据上测得准，换到真实分布可能掉到一半以下。

### 第 2 步　训练（被训练：查错器的参数）

**模型选择**（两张 5090 的现实范围）：
- 最省：中文医学 BERT 级模型做逐 token 标注（哪个词是错的）加错误类型分类。单卡几小时；
- 居中：0.5—1.5B 的开源生成式模型全参微调，输出 JSON 格式的错误列表。单卡一天以内；
- 上限：7—8B 模型做 LoRA 微调，单卡可行，一到两天。

**损失**：生成式查错器用的就是普通的下一个词交叉熵。输入是"记录 + 病历片段"，目标输出是上面那个 `label` 的 JSON 文本。模型每预测错一个词就产生损失，梯度下降改参数，与 Prometheus 训练评委的方法完全相同。

### 第 3 步　考查错器本身（元评测）

| 考法 | 报告什么 |
|---|---|
| 留出的埋雷集（错误类型在训练时见过） | 按类型的召回率、精确率 |
| 留出的埋雷类型（训练时没见过的类型） | 泛化能力 |
| 生成器自然犯错的样本，医生标注 | 与医生的宏 F1 或 κ，以及医生之间的一致性作对照 |
| 对照组 | 规则表单独用；GPT-4o 直接当评委；你的查错器 |
| 分方法报告 | 在每一种被比较的生成方法的输出上分别算一致性（工具箱第 5 节） |

### 第 4 步　怎么用它

1. **评测**：作为独立评委，评所有对比方法，包括 LLM-CARe、NHS 等的复现版本。它和任何生成器都不是同一家，满足合同 3；它的训练数据与任何被评方法的优化目标无关，满足合同 2。
2. **过滤**：生成 N 份，挑查错器报错最少的一份，相当于 ProGen、SunGen 那条去噪线的现代版本（见第四讲）。
3. **奖励**：程序规则分 + 查错器分 + 少量 RaR 式评委分，加权作为 GRPO 的奖励（路线 C）。

**一句话**：LLM-CARe 让同一个模型按同一份清单自查、自改、自评；你用自动埋雷训练出一个独立、可校准、能在本地跑的查错器，把这三件事拆开。这是你相对于那几篇最直接的升级。
